Constraints tell you the intended solution — read them first

Default ceiling is n, q ≤ 10⁵ (→ O(n log n) or O(n)) with values to 10⁹. But a big minority of problems deliberately cap N ≤ 200–1000 — the 2026 set's MSS-with-swaps is N ≤ 500, Lock & Parity is N ≤ 200. Small N is the setter telling you O(n²) is intended. Tomorrow: constraints first, then choose the approach — don't hunt for cleverness the limits don't demand.

Output-contract traps — your TCS failure mode, now with receipts

  • "Sum of answers to all queries, mod 10⁹+7" — one aggregated integer, not per-query lines. Appears in 5 of 17 stdin-style HWI problems. The single most repeated trap in the corpus.
  • Literal sentinel strings baked into expected output: "Hamiltonian path does not exist", "X Score not found." — exact match, punctuation included.
  • Floats to exactly 2 or 6 decimals (53.33, 0.504000) → f"{x:.2f}" / f"{x:.6f}".
  • -1 sentinels for impossible cases, recurring across BFS/reachability problems.
  • Format is not standardized between problems — space-separated vs line-separated varies. Re-read the Output Format block every problem.
  • Raw stdin/stdout throughout — no LeetCode-style function stubs (one set layers a get_ans signature on top; one of its problems says "YES" per query in the text but actually wants the count of YES queries as a single integer).
Python-specific: at n, q ≤ 10⁵, input() is dangerously slow. Template: import sys; data = sys.stdin.read().split(), walk an index pointer, batch output with print("\n".join(out)). Apply % 1000000007 at every accumulation, not once at the end.

Output contract — your known failure mode

"Passing sample test cases does not guarantee final acceptance."

Direct from the Jan 2026 candidate. Hidden tests and edge cases decide it — and this is exactly how you lost the TCS Easy this morning: correct logic, wrong output format. You printed a Python dict repr where a compact literal was required, and exact-match failed every case.

Tomorrow that mistake is worth ₹7 LPA. It is the single highest-probability way to lose a problem you have actually solved.

The rule — never print a container: 
print(d)              # {1: 1, 2: 1}   Python inserts spaces  ✗
print([50, 60])       # [50, 60]       same problem           ✗

print("{" + ",".join(f"{k}:{v}" for k,v in d.items()) + "}")   ✓
print("[" + ",".join(map(str, xs)) + "]")                      ✓
print(" ".join(map(str, xs)))                                  ✓
Pre-submit checklist — 60 seconds per question, every question:
  1. Re-read the required output format in the statement. Not the sample — the specification.
  2. Compare one line of your real output against it character by character. Spaces, brackets, separators, case.
  3. Run the edge cases nobody gives you: empty input, single element, zero, all-identical values, maximum constraint.
  4. Confirm you print nothing extra — no prompts, no labels, no debug lines left in.
  5. Check integer vs float. If the spec says 2 decimals, use f"{x:.2f}".

Unlike TCS, there's no reported no-edit-after-compile rule here, so you can iterate. But the same discipline still pays: with 3 hours and 3 problems, minutes spent debugging a formatting error are minutes stolen from the Hard.
