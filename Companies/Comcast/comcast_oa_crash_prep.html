SQL Drill — the highest-confidence topic

Both reports call out SQL explicitly, including "write 5 queries, joins + subqueries" live in the technical interview. Assume you'll be asked to write SQL by hand, not just recognize it in an MCQ.

Schema: employees(id, name, dept_id, salary, manager_id), departments(id, name)
Q1. List each department's name with its average salary, only for departments with more than 3 employees.
Reveal answer 
SELECT d.name, AVG(e.salary) AS avg_salary
FROM departments d
JOIN employees e ON e.dept_id = d.id
GROUP BY d.name
HAVING COUNT(e.id) > 3;

HAVING filters after GROUP BY (WHERE can't reference an aggregate). Common trap: using WHERE COUNT(...) — that fails.

Same schema
Q2. Find employees who earn more than their own manager.
Reveal answer 
SELECT e.name
FROM employees e
JOIN employees m ON e.manager_id = m.id
WHERE e.salary > m.salary;

Self-join — the same table joined to itself via manager_id → id. This exact shape ("compare a row to a related row in the same table") is a classic Comcast-style ask.

Same schema
Q3. List employees who earn more than the average salary of their own department, using a subquery (not a window function).
Reveal answer 
SELECT e.name
FROM employees e
WHERE e.salary > (
  SELECT AVG(e2.salary) FROM employees e2 WHERE e2.dept_id = e.dept_id
);

Correlated subquery — the inner query re-runs per outer row, referencing the outer row's dept_id. This is the "subqueries" half of "joins and subqueries" — practice this shape specifically.

Same schema
Q4. List departments with no employees at all.
Reveal answer 
SELECT d.name
FROM departments d
LEFT JOIN employees e ON e.dept_id = d.id
WHERE e.id IS NULL;

LEFT JOIN + IS NULL is the standard "find the missing side" pattern — an INNER JOIN here would silently drop empty departments instead of surfacing them.

Same schema
Q5. Get the second-highest salary in the company without using LIMIT/OFFSET.
Reveal answer 
SELECT MAX(salary) AS second_highest
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);

Nested MAX — a very common "gotcha" SQL question precisely because LIMIT/OFFSET isn't portable across every DB engine.

CS Fundamentals — rapid fire

Both reports confirm MCQs on DBMS, OS, CN, Linux, DS. This is recall speed, not derivation — treat it as a 30-minute refresh, not new learning.

DBMS — Normalization1NF: no repeating groups. 2NF: no partial dependency on a composite key. 3NF: no transitive dependency on a non-key column. Know why you'd denormalize anyway (read-heavy, avoid join cost).
DBMS — ACIDAtomicity, Consistency, Isolation, Durability. Isolation levels: Read Uncommitted → Read Committed → Repeatable Read → Serializable, each fixing a specific anomaly (dirty read, non-repeatable read, phantom read).
OS — DeadlockFour necessary conditions: mutual exclusion, hold-and-wait, no preemption, circular wait. Break any one → no deadlock.
OS — Process vs ThreadProcess: own memory space, heavyweight context switch. Thread: shares memory with siblings, lightweight switch. Threads within a process share heap/data, each has its own stack.
OS — Paging vs SegmentationPaging: fixed-size blocks, no external fragmentation, may have internal fragmentation. Segmentation: variable-size logical units, opposite trade-off.
CN — TCP vs UDPTCP: connection-oriented, reliable, ordered, slower (3-way handshake). UDP: connectionless, no guarantee, faster — used where speed beats reliability (video/voice).
CN — OSI layersPhysical → Data Link → Network → Transport → Session → Presentation → Application ("Please Do Not Throw Sausage Pizza Away"). Know which layer does what: IP=Network, TCP/UDP=Transport, HTTP=Application.
CN — DNSResolves domain name → IP address, hierarchical (root → TLD → authoritative), cached at multiple levels (browser, OS, resolver).
DS — Array vs Linked ListArray: O(1) random access, O(n) insert/delete mid-sequence. Linked List: O(n) access, O(1) insert/delete at a known node. Know when each wins.
DS — Stack vs Queue use casesStack: LIFO — undo, recursion/call stack, balanced-brackets. Queue: FIFO — BFS, task scheduling, print spooling. This exact question ("describe two data structures with a real example") was asked verbatim in one report.
Linux — basic commandsgrep (search text), chmod (permissions), ps/top (processes), kill -9 (force-terminate), chmod 755 means owner rwx, group/others r-x.
Linux — permissionsrwxr-xr-- reads as owner=rwx, group=r-x, others=r--. Numeric: r=4, w=2, x=1, sum per triplet.

Coding — easy-medium, matching reported topics

Not predicted verbatim questions — practice problems in the same shape as what both reports named: palindrome check, "second maximum element," sorting complexity.

Q1 · Palindrome check — Given a string, determine if it's a palindrome, ignoring case and non-alphanumeric characters.
Reveal approach

Two pointers from both ends, skip non-alphanumeric, compare lowercased chars, converge to the middle. O(n) time, O(1) space. The named report explicitly expects a two-pointer solution — don't reach for string reversal + comparison, name the two-pointer approach out loud.

Q2 · Second maximum element — Given an array, find the second-largest element without sorting.
Reveal approach

Single pass, track max1 and max2. If current > max1: max2 = max1, max1 = current. Else if current > max2 and current != max1: max2 = current. O(n) time, O(1) space — sorting would be O(n log n), a slower "correct but suboptimal" answer they're explicitly testing for.

Q3 · Sorting complexity, cold — State time/space complexity (best/avg/worst) for Bubble Sort, Merge Sort, Quick Sort, and when you'd pick each.
Reveal answer

Bubble: O(n²) all cases, O(1) space — never use it, know why it's bad. Merge: O(n log n) all cases, O(n) space — stable, good for linked lists / external sorting. Quick: O(n log n) avg, O(n²) worst (bad pivot), O(log n) space — fastest in practice, in-place. "Different sorting algorithms, be good at time/space complexity" was named directly in one report.
